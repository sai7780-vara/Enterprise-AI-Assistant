# Phase 2 Learning Guide — Local RAG (Retrieval-Augmented Generation)

## 1. What Problem Was Not Solved in the Previous Phase
In Phase 1, we built a standard chatbot. However, the LLM was entirely ungrounded:
- It could not read local company documents, policies, or user-uploaded files.
- It was prone to hallucinating facts about specific company regulations.
- It had no concept of proprietary data.

## 2. Why This Phase Was Needed
To build an *Enterprise* AI Assistant, the AI must have access to internal documents. **Retrieval-Augmented Generation (RAG)** solves this by retrieving relevant text chunks from uploaded documents and presenting them as ground truth in the LLM's prompt. 

We needed a local, self-contained RAG setup to avoid complex cloud database costs during development and to ensure all data remains on the user's machine (Local RAG).

## 3. Technical Skills Used in This Phase
* **Document Parsing:** Reading and extracting text from PDFs (`pypdf`), Text files, and Markdown files.
* **Text Chunking:** Splitting raw text into smaller overlapping segments (e.g. 500-1000 characters) so they fit within the embedding model's context constraints.
* **Vector Embeddings:** Translating semantic text meaning into high-dimensional vector arrays using Gemini `text-embedding-001`.
* **Vector Indexing (FAISS):** Creating an in-memory index (`faiss-cpu`) to perform ultra-fast nearest-neighbor similarity searches using L2 normalization and Inner Product (resulting in Cosine Similarity).
* **Python Serialization (Pickle):** Saving embedded text chunks and metadata locally to a file (`knowledge_store.pkl`) to persist state across server restarts.

## 4. What Was Implemented in This Phase
* **Document Ingestion Service:** An endpoint (`POST /api/documents/upload`) that parses files, chunks text, generates embeddings, and saves them.
* **Local Vector Store (`vector_store.py`):** Wraps FAISS index creation, saving, loading, adding, deleting, and searching documents.
* **Semantic Search query pipeline:** Converts a user query into a vector and retrieves the top-4 closest chunks.
* **Context Grounded Chat:** Automatically retrieves context chunks for the user's query and injects them into the Gemini prompt template.

## 5. What This Phase Still Cannot Do
* **No Page Citations:** The UI displays a synthesized response but does not show *which* files or pages were retrieved.
* **No Source Validation:** The user has no way of checking where a statement came from.
* **Hardcoded Retrieval:** The number of retrieved chunks (`top_k = 4`) is hardcoded in the backend.
* **No Confidence Indicators:** The user has no sense of how well the retrieved chunks actually match their query.

## 6. What is Moved to the Next Phase
In **Phase 3 (Production RAG)**, we will solve these usability gaps by:
- Storing and retrieving page numbers for chunks.
- Exposing a dynamic `top_k` slider on the React UI.
- Calculating and displaying similarity confidence percentages.
- Building expandable "source citation cards" showing file names and page ranges.

## 7. Beginner-Friendly Questions & Answers

### Q1: Why do we split documents into small "chunks" instead of feeding the whole file?
**A:** LLM prompt lengths and embedding models have physical limits. Feeding a whole 50-page document into a vector model would lose semantic focus and dilute the search results. Splitting the document into smaller chunks ensures we only retrieve and pay for the exact paragraphs that answer the query.

### Q2: What is a Vector Embedding, and how does similarity search work?
**A:** A vector embedding is an array of numbers (e.g., length 3072) generated by an AI model that represents the semantic meaning of a text. Texts with similar meanings (e.g., "vacation days" and "annual leave") will have vectors that point in nearly the same direction in multi-dimensional space. We use math (cosine similarity/inner product) to find the vectors closest to our query vector.

### Q3: Why do we normalize vectors using L2 normalization in FAISS?
**A:** When vectors are normalized to unit length (L2 norm = 1), their Inner Product (dot product) becomes mathematically identical to Cosine Similarity. This allows us to use FAISS's highly optimized `IndexFlatIP` (Inner Product) to perform fast cosine similarity searches.

### Q4: What are the risks of using Python's `pickle` library for local storage?
**A:** `pickle` is great for simple local serialization but is not secure against untrusted files. If a malicious user modifies the `knowledge_store.pkl` file, loading it can execute arbitrary shell code. In a production environment with public users, database systems (like PostgreSQL/pgvector) are preferred.

### Q5: How does a RAG prompt system look in practice?
**A:** We construct a prompt template like this:
```
You are a helpful assistant. Use the following context to answer the user's question. If you do not know the answer, say so.

--- CONTEXT ---
[Retrieved Chunk 1...]
[Retrieved Chunk 2...]
---------------

USER QUERY: [User's question]
```
This forces the model to ground its generation in the provided text.
